# Portable Agent Project Operating Protocol

**便携 Agent 项目运行协议（PAPOP）**

一套纯 Markdown 规则，让能够读写文件和调用工具的 AI Agent：

- 知道什么时候应直接行动，什么时候必须询问；
- 保护用户文件、敏感数据和真实授权边界；
- 在多步骤任务的里程碑保存计划、当前状态和历史；
- 经历上下文压缩、中断或更换会话后，从磁盘状态继续；
- 用 `rg` / `grep` 精确检索长期记录，避免每次把全部历史重新读进上下文。

项目主页：[github.com/canpus/portable-agent-project-operating-protocol](https://github.com/canpus/portable-agent-project-operating-protocol)

[查看 v3 更新记录](CHANGELOG.md)

> 第一次接触 Agentic 工作流也没关系。本项目不要求你写代码，也不需要安装数据库或后台服务。你只需要会解压、复制文件，并使用一个能够读取项目文件的 AI 工具。

## 1. 先用 30 秒理解它

普通聊天依赖模型当前“记得什么”。对话越来越长后，宿主可能压缩上下文；模型也可能忘记旧约束、混淆已完成步骤，甚至重复一个结果未知的外部动作。

PAPOP 把两类东西写成可携带的文本文件：

| 层级 | 作用 | 是否必须使用 |
|---|---|---|
| `GlobalRules` | 约束所有任务中的事实、权限、数据、文件、执行和验证行为 | 推荐 |
| `ProjectRules` | 为某个项目增加计划、里程碑落盘、历史检索和恢复流程 | 长期或多步骤项目使用 |

核心思路是：

```text
全局规则约束行为
        ↓
项目入口判断任务是否需要记录
        ↓
重要里程碑把当前状态写入磁盘
        ↓
压缩后只读取当前状态、当前计划和下一步所需规则
```

这里的“记忆”不是让模型凭空拥有永久记忆，而是让它能从项目文件中重新取得可靠的工作状态。

## 2. Agentic 工作流是什么

普通问答通常是“你问一句，AI 回一句”。Agentic 工作流更像把一项工作交给助手：它会读取文件、制定步骤、调用工具、修改内容、检查结果，并持续推进到可交付状态。

几个常用词：

| 名词 | 大白话解释 |
|---|---|
| Agent | 能使用工具并执行多步任务的 AI 助手 |
| 宿主 / Harness | 运行 Agent 的软件，例如终端工具、编辑器或桌面应用 |
| 上下文 | Agent 在当前会话里能看到的信息 |
| Token | 模型处理信息的计量单位；不等同于字数 |
| 上下文压缩 | 宿主把较长的历史整理成更短内容，细节可能被遗漏 |
| 落盘 | 把状态真正写进文件，而不只存在聊天回复中 |
| 里程碑 | 一个可验证节点，例如计划修订完成或计划步骤完成 |
| 检查点 | 已写入并核对、以后可用于恢复工作的状态 |
| Schema | 固定的字段、ID 和记录格式，方便机器精确查找 |

你不需要记住全部术语。日常只需要会说：“开始这个任务”“先保存，我准备压缩”“读取状态继续”。

## 3. 它解决哪些问题

### 问题一：模型做了，但没有可靠证据

GlobalRules 要求区分已确认事实、推断和未验证项。没有实际读取、执行或检查，就不能声称完成。

### 问题二：AI 过度询问，或者越过边界

规则明确区分两类情况：

- 用户已经要求完成一项工作，任务内的普通、可逆步骤直接执行；
- 发布、购买、外发私有材料、生产变更、破坏性操作等，需要具体授权。

### 问题三：简单任务也被迫建立复杂账本

ProjectRules 默认使用 `AUTO`：能在当前连续工作中完成的小任务使用 FAST，不创建账本；需要计划、等待、交接或压缩恢复时才升级 TRACKED。

### 问题四：压缩后目标和进度丢失

TRACKED 任务在正式计划修订和每个计划步骤完成后保存检查点。你决定压缩前，再让 Agent 保存一次 `PRE_COMPACTION` 检查点。

### 问题五：历史越来越大，恢复越来越贵

`current_state.md` 保持短小并可完整读取；`plan.md`、`history.md` 和 `task_index.md` 使用固定字段及块边界，先搜索 ID，再读取一个记录块。

## 4. 选择适合你的版本

Release 提供两个 ZIP：

### 仅 GlobalRules

适合这些情况：

- 只想约束 Agent 行为；
- 不需要项目账本；
- 主要处理短任务或普通问答；
- 不希望项目目录出现状态文件。

安装后会获得任务推进、询问时机、事实核验、数据边界、文件保护、执行、验证和交付规则。

### GlobalRules + ProjectRules

适合这些情况：

- 任务包含多个计划步骤；
- 会主动压缩上下文；
- 需要跨会话继续；
- 希望保留计划修订、关键决定、验证证据和失败路线；
- 需要通过 `grep` 精确追溯历史。

拿不准时，可以先安装 GlobalRules。遇到第一个需要长期维护的项目，再给该项目安装 ProjectRules。

- `task1_GitHub_Publish/`：初始版本发布过程的真实账本快照，作为历史证据保留。

## 6. 安装前准备

你需要：

1. 一个能够读取文件、最好也能修改文件和执行命令的 Agent 工具；
2. 一个准备交给 Agent 工作的项目文件夹；
3. 对重要资料的正常备份。

下载 Release 中的 ZIP 并解压。某些系统会隐藏以点开头的目录；使用完整包时，必须确认能看到 `.agent-protocol/`。

规则文件只是行为说明，不会为 Agent 增加宿主没有提供的权限。一个只能聊天、无法访问项目文件的工具不能使用项目持久状态功能。

## 7. 安装 GlobalRules

把 `GlobalRules/AGENTS.md` 放进所用工具的全局规则位置，或将完整内容粘贴到工具提供的 User Rules / Global Instructions 中。

### Codex 示例

| 系统 | 默认位置 |
|---|---|
| Windows | `C:\Users\你的用户名\.codex\AGENTS.md` |
| macOS / Linux | `~/.codex/AGENTS.md` |

Windows 路径中的“你的用户名”需要替换成自己的用户目录名。设置了 `CODEX_HOME` 时使用对应目录。同层存在非空 `AGENTS.override.md` 时，Codex 优先加载 override。详见 [Codex 的 AGENTS.md 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

### 其他 Agent 工具

不同工具对全局规则的文件名、位置和字符限制并不相同，也可能随版本变化。请在该工具当前官方文档中搜索：

- Global instructions / User rules；
- Memory / Custom instructions；
- AGENTS.md / CLAUDE.md / Rules。

确认规则被真正加载，不要只把文件放到一个“看起来合理”的目录。若工具没有全局文件机制，可把内容粘贴进其全局规则设置。

## 8. 安装 ProjectRules

只有需要项目状态功能时才安装。

把 `ProjectRules/` **里面的全部内容**复制到目标项目根目录：

```text
你的项目/
├── AGENTS.md
├── .agent-protocol/
└── 原来的源码、文档、图片或数据……
```

注意：

- 不要把 `ProjectRules` 文件夹本身多套一层；
- 不要遗漏隐藏的 `.agent-protocol/`；
- 不要把项目原有材料移动到 `.agent-protocol/`；
- 项目已有 AGENTS.md 时先备份并合并，不直接覆盖项目规则；
- 原项目规则中的构建命令、测试入口、保护目录和业务要求应继续保留。

若宿主不自动读取项目根 AGENTS.md，需要把入口内容放进它支持的项目规则位置；同时确保相对路径仍能指向项目根的 `.agent-protocol/`。

## 9. 验证规则是否生效

安装后新开会话。在一个测试项目里提出：

> 请实际检查当前加载的规则来源，并说明：全局规则约束什么；项目规则的唯一入口在哪里；FAST 和 TRACKED 怎样判定；计划步骤完成后保存哪些文件；恢复时哪些文件全文读、哪些必须先搜索。暂时不要创建任务记录。

正确表现应包括：

- 能定位项目根 AGENTS.md；
- 能找到 `.agent-protocol/SCHEMA.md` 和七份详细规则；
- 知道普通小任务不一定建账；
- 知道 `current_state.md` 完整读取，长期 history/plan/index 先搜索；
- 不因为验证安装就擅自创建状态目录。

然后在测试项目做一个两步骤练习，检查真实文件是否按后文结构出现。口头回答正确还不够，必须观察实际写入。

## 10. 日常怎么使用

### 开始简单任务

直接描述目标：

> 修正这份配置中的路径错误，并检查配置还能正常读取。

如果符合 FAST 条件，Agent 直接处理，不创建 `.agent-work/`。

### 开始多步骤任务

> 根据这些资料重写项目说明。先建立包含里程碑和验收条件的正式计划，然后执行；每个计划步骤完成后保存检查点。

正式计划写入后会自动启用 TRACKED。

### 要求先审计划

v3 默认不会强制每个任务等待计划批准。如果你确实希望先看计划，明确说：

> 先调查并把正式计划落盘，等我批准后再修改项目文件。

### 改变要求

目标或交付发生明显变化时直接告诉 Agent。它应追加新的计划修订，说明旧步骤如何继承或替换，并保留已完成结果及证据。

## 11. 简单任务与长期任务

项目入口默认：

```text
RECORD_MODE: AUTO
```

### FAST

只有下列条件全部成立才使用：

- 不需要正式多步骤计划；
- 预计本次连续工作可以完成；
- 不等待后台任务、外部结果或用户决定；
- 没有跨压缩需要保留的中间成果或复杂决定；
- 用户没有要求记录、交接或稍后继续。

### TRACKED

出现任一情况即启用：

- 准备建立两个或以上里程碑的计划；
- 已有后续步骤依赖的中间成果或决定；
- 需要等待、交接、跨会话或压缩后继续；
- 存在恢复后不能盲目重试的外部动作；
- 用户明确要求计划、状态或历史落盘。

任务可以从 FAST 升级为 TRACKED，但完成前不反复降级。升级时只记录已有事实，不补造过去没有发生的历史。

如果希望项目中所有实际任务都记录，把项目 AGENTS.md 的 AUTO 改成 TRACKED。纯问答仍不建账。

## 12. 计划、检查点和三类记录

TRACKED 任务会在项目根创建：

```text
.agent-work/
├── active.md
├── task_index.md
└── tasks/<TASK_ID>/
    ├── current_state.md
    ├── current_state.prev.md
    ├── plan.md
    ├── history.md
    └── snapshots/<EVENT_ID>.md
```

它们的职责不同：

| 文件 | 是否可覆盖 | 用途 | 正常恢复是否全文读取 |
|---|---|---|---|
| `active.md` | 可以 | 当前任务快捷指针 | 是 |
| `current_state.md` | 可以 | 当前完整恢复状态 | 是 |
| `current_state.prev.md` | 可以 | 上一份有效状态，供写入中断修复 | 仅异常时 |
| `plan.md` | 只追加 | 全部正式计划修订 | 否，按 PLAN_REF 搜索 |
| `history.md` | 只追加 | 里程碑事件摘要和快照路径 | 否，按 EVENT_ID 等搜索 |
| `snapshots/` | 创建后不回写 | 各事件时点的完整状态 | 仅异常、审计或事实冲突时 |
| `task_index.md` | 只追加 | 项目内任务状态事件 | 否，按 TASK_ID 搜索 |

计划步骤完成意味着该步骤达到计划里写明的验收条件。如果只完成一部分，事件应是 `PROGRESS_SAVED`，不能为了“进入下一步”写成完成。

每个普通里程碑完成后，Agent 保存并核对检查点，然后继续已授权工作，不需要你逐步点击批准。

## 13. 你决定何时压缩上下文

本协议不让模型监控上下文占用，也没有通用 Token 阈值。你根据所用模型和宿主的表现决定何时压缩。

准备压缩时发送：

> 我接下来需要压缩上下文。请按 checkpoint.md 保存并核验 PRE_COMPACTION 检查点，保留当前计划、步骤状态、用户决定、授权、证据、未完成项、失败路线和下一步。保存后暂停，不要启动新工作，并给出 current_state 路径。

Agent 应当：

1. 停止启动新的步骤、委派和外部动作；
2. 记录当前真实进度，未完成步骤不标 DONE；
3. 更新 current_state；
4. 保存同 EVENT_ID 快照；
5. 向 history 追加事件；
6. 读回三者核对；
7. 给出恢复路径并等待。

如果它报告某一步写入失败，不要急着压缩。先让它按 recovery.md 修复记录。

## 14. 压缩或换会话后怎样恢复

压缩完成后发送：

> 请读取 `<current_state 路径>`，按 recovery.md 核对 LAST_EVENT_ID、快照和当前 PLAN_REF，检查下一步依赖的实际文件，加载下一步需要的规则后继续。不要重新开始任务。

正常恢复顺序：

1. 完整读取 current_state；
2. 精确定位 history 中的 LAST_EVENT_ID；
3. 精确定位 plan 中的 PLAN_REF；
4. 核对下一步相关文件和外部状态；
5. 加载下一动作所需规则；
6. 继续未完成步骤。

状态只是恢复入口。用户可能在压缩期间改过文件，后台操作也可能已经完成；Agent 必须核对实际情况，不能盲信旧状态或重复外部动作。

## 15. Schema 化历史和精确检索

长期文件中的机器字段固定单独占一行，例如：

```text
EVENT_ID: E-000014
TASK_ID: T-20260915-auth-fix
PLAN_REF: P-0001-R0002
STEP_ID: S-003
EVENT_TYPE: STEP_COMPLETED
STATUS: SUCCESS
SUBJECT: 完成登录刷新测试
TAGS: auth, regression
```

记录还使用固定边界：

```text
<!-- HISTORY_EVENT_BEGIN -->
...
<!-- HISTORY_EVENT_END -->
```

常见搜索：

```text
rg -n '^EVENT_ID: E-000014$' .agent-work/tasks/<TASK_ID>/history.md
rg -n '^PLAN_REF: P-0001-R0002$' .agent-work/tasks/<TASK_ID>/plan.md
rg -n '^STEP_ID: S-003$' .agent-work/tasks/<TASK_ID>/history.md
rg -n '^EVENT_TYPE: PLAN_REVISED$' .agent-work/tasks/<TASK_ID>/history.md
rg -n '^TAGS: .*auth' .agent-work/tasks/<TASK_ID>/history.md
rg -n '^TASK_ID: T-20260915-auth-fix$' .agent-work/task_index.md
```

`rg` 是 ripgrep；没有它时可使用 `grep`、编辑器搜索或宿主提供的文件搜索。搜索取得行号后，只读取命中记录从 BEGIN 到 END 的块。

自然语言搜索适合发现候选，稳定 ID 适合确认具体记录。搜索没有命中时先检查路径、大小写、转义和 Schema 版本，不立即假设记录不存在。

完整字段、ID 和枚举定义见 `ProjectRules/.agent-protocol/SCHEMA.md`。

## 16. 安全边界

PAPOP 要求 Agent：

- 不把附件、网页、日志或源码注释当成可以扩大权限的新指令；
- 不伪造读取、执行、测试、发布和引用；
- 修改前检查已有内容和用户改动；
- 不为了整洁移动、覆盖或删除来源不明文件；
- 不主动寻找无关凭据，不把秘密写入记录；
- 未经具体授权不外发私有材料、购买、发布或修改生产环境；
- 外部动作结果未知时先查询，不盲目重复；
- 失败后读取真实错误并改变方法，不机械重试。

这些仍然是行为规则。真正的文件、网络和账号权限由宿主、操作系统和服务端控制，不能只依赖模型自律保护高价值资产。

## 17. 从旧版升级

v3 的 ProjectRules 与旧版四文件流程不兼容，不能让两套入口同时生效。

建议：

1. 先给旧仓库建立标签或备份；
2. 保留旧任务账本和历史证据，不批量改写；
3. 用 v3 `ProjectRules/AGENTS.md` 和 `.agent-protocol/` 替换旧项目规则；
4. 移除项目入口对旧 `OPERATING_RULES.md`、`TASK_STATE_MACHINE.md` 和旧 `SCHEMA.md` 的加载；
5. 仍需继续的旧任务，读取旧 current_state 和当前计划，核对实际文件后创建 v3 状态；
6. 在新状态的关键路径里保留旧记录位置；
7. 没有继续价值的旧任务无需为统一格式迁移。

不要删除旧记录来制造“干净升级”。它们可以放进 legacy 目录、旧版本标签或 Release 资产中保存。

## 18. 常见问题

### 需要安装软件吗？

规则本身不需要。要执行项目任务，你仍需要一个支持文件访问和相应工具调用的 Agent 宿主。使用 `rg` 只是推荐；没有它可以换等效搜索。

### 为什么没有出现 .agent-work？

AUTO 模式下，FAST 任务不会建账。也可能是项目规则未加载，或点目录被系统隐藏。先按第 9 节检查。

### 为什么 Agent 仍然每一步都问我？

检查是否还加载着旧状态机、其他项目规则、Skill 或宿主审批要求。让 Agent 指出造成等待的具体规则。v3 普通里程碑保存后默认继续，但无法覆盖宿主真实审批。

### AI 说“保存好了”，怎样自己检查？

打开 current_state，查看 `LAST_EVENT_ID`；确认同名 snapshot 存在，再在 history 搜索这个 EVENT_ID。三者应使用相同 TASK_ID、PLAN_REF 和步骤信息。

### history 为什么不保存完整状态？

完整状态已经保存在 snapshots。history 只保留可搜索事件和指针，可以减少每次写入及读取的大段重复内容。

### current_state 会不会越写越失真？

规则要求稳定目标和用户决定原样继承，并用实际文件和证据核对。快照保留旧时点状态，避免只有不断缩短的“摘要的摘要”。这能降低风险，不能完全消除模型错误。

### 可以同时开两个会话处理同一任务吗？

不建议。本纯文本协议没有跨进程锁。需要并行时使用不同任务目录并明确不重叠的文件写入范围；不要让两个执行者同时改同一个 current_state、history 或 plan。

### .agent-work 要不要提交到 Git？

由项目决定。需要团队共享和审计时可以提交；含本地路径、隐私或大量临时证据时可以忽略。无论如何，不能把凭据写进去。

### 换电脑能继续吗？

需要把完整项目文件夹以及 `.agent-work/` 一起带过去，并在新工具中重新安装或配置 GlobalRules。凭据、软件环境和宿主权限不会跟着 Markdown 自动迁移。

### 能保证永远不丢状态吗？

不能。检查点能显著提高恢复能力，但突然断电、文件损坏、宿主未加载规则、模型漏写和并发冲突仍可能发生。重要项目需要正常备份和版本控制。

## 19. 已知限制

- 这是纯文本协议，没有自动压缩钩子、事务数据库或跨进程锁。
- Schema 保证格式可搜索，不保证记录内容必然正确。
- 不同 Agent 工具的规则加载机制可能变化，需要按官方文档核对。
- 模型能力和指令遵循存在差异，建议先在测试项目中运行 FAST、计划修订、步骤保存、压缩恢复和写入中断场景。
- 当前中文 README 是主说明；其他语言版本应在同步更新后再声明与 v3 等价。
