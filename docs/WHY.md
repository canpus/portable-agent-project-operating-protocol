# 为什么这样设计（WHY）

这份文档解释 PAPOP 为什么长成现在这样：它想解决什么问题、每套机制在对付什么毛病、以及作为使用者你需要做什么。

只想了解怎么安装和使用，看 [README](../README.md) 和 [安装说明](INSTALL.md) 就够了；这份文档回答的是"为什么"。

---

## 简单来说

我用 AI 干活的时候，被它坑过几次：聊到一半突然"失忆"、干着干着跑偏、最后我根本不知道它到底动了什么。后来我搞了这套规则文件，专门治这几种毛病。

它不是软件，不用安装，就是几个 Markdown 文本文件，丢进项目里，AI 每次开工自己读。

## 一、它解决了哪些问题

### 1. 上下文一压缩、一换模型，之前聊的全忘光

**问题**：AI 的"记忆"就是一个长度有限的上下文窗口。聊长了客户端就会压缩它；或者你换了个模型、换了个窗口，前面说过什么、做到哪，全没了。

**解决**：把记忆从它脑子里搬到磁盘上。项目里会有一个 `.agent-work/` 目录专门放账本。每到一个里程碑（计划写完、一个步骤做完、你做一个关键决定、准备交付、遇到等待、做外部动作前后），AI 就把当前状态写一遍。压缩能压掉它脑子里的东西，压不掉硬盘上的文件。

账本里有这么几样：

| 文件 | 作用 |
|------|------|
| `current_state.md` | **当前状态**，短小但完整：项目现在什么样、做到哪一步、下一步该干嘛 |
| `plan.md` | **计划**，只追加；每次改计划都是新加一整块，旧的不动 |
| `decisions.md` | **你的决定**，每次你说"批准""验收通过""这个可以发"，它都记下来，并精确绑定到当时那份计划或那个交付版本 |
| `history.md` | **里程碑事件**，只追加，每次只记"这次变化了什么"，不重复抄全文 |
| `snapshots/` | 每次存档时把当前状态**原样复制**一份存起来，存完不许改 |

### 2. 上下文一长就注意力涣散，忘了当下该干啥

**解决**：靠 `current_state.md`。它的核心要求是"短小 + 完整 + 随时可读"——必须一读就知道三件事：已经干完了什么、项目现在什么状态、下一步该做什么。AI 接着干活之前先读它，不用去翻几万行的历史。

### 3. 干着干着目标漂移，忘了最初要做啥

**解决**：靠 `plan.md` 加上你的批准。规则要求它动手改东西之前，必须先把计划写下来给你看；你点头了才能施工。计划是一块一块追加的，每一块都自带目标、范围、不做什么、步骤、每一步怎么算做完。

这里有个关键设计：**写了新计划不等于你已经批准**；而且你批准的是"那一版"，它改一版你就得重新批一次——老的批准不能自动挪给新版本。这样它就没法偷偷改目标。

### 4. 历史越滚越大，全读一遍又费钱又污染上下文

**解决**：给记录定死字段格式，然后**用搜索定位，只读那一小段**。每条记录都有固定标签（任务 ID、计划版本号、事件 ID、状态、主题等）。要用历史的时候，它先 `grep` 搜 ID 定位，只读那一段（几十行），不整份加载。历史本身也只存"这次变了什么"外加一个快照指针，不重复抄整份状态。

### 5. 不知道它到底干了什么，怕它乱来

**解决**：几道锁扣在一起——

- 动手前必须有你批准的计划（"计划审批"模式）；
- 做完一步就得立刻把账本更新掉；
- 交付之后要**你验收**，而且规则里写死了：**它自己检查通过只能证明它自己验过，不能替你说"验收通过"**；
- 涉及对外动作（发布、发消息、买东西、改生产环境）要单独授权，执行前后都记一笔；结果不确定时（发出去了但不知道成没成）**先去查，不许重复发送**；
- 你随时可以指定关卡，比如"发布前等我确认"——这种关卡它**不能自己判断"不重要了"就撤掉**，只有你明确放行才放行。

### 6. 不是所有项目都值得这么重

**解决**：分档。

- **计划审批模式（Plan Approval）**：正经项目用，关键节点都要你点头；
- **任务委托模式（Task Delegation）**：你只想给个目标让它自己推进时用——它在你划定的范围内自己干，只在缺关键决定、缺具体授权或遇到你设的关卡时才停下来问；
- **FAST**：能一口气做完的小活不建账，直接干完给你看。

## 二、需要你做的事

### 1. 盯着点上下文，该压缩的时候主动喊停

这套规则里，**AI 不估算 token、也不设固定阈值**（这是故意的——不同模型、不同客户端的极限都不一样，写死一个数字反而误导）。所以这件事归你：看着客户端的上下文用量差不多了，就跟它说：

> 把当前状态落盘，上下文有点长了，我要手动压缩了。

它会把账本保存、核对一遍，然后**停下来等你**。你确认存好了，手动执行压缩（例如 `/compact`），压缩完再跟它说：

> 继续

它会读 `current_state.md`，核对实际文件，接着往下干。注意：**没释放的关卡、还没验收的交付，压缩完照样还在**，不会因为压缩就"默认通过"。

### 2. 它找你批计划的时候，认真看

这是整套东西最值钱的地方，别偷懒。觉得行就回"批准"；觉得不行就直接说哪不行、你想怎么改——它会重新出一版给你，你再批。**只有你说"批准"才算数**，它自己说"我理解你的需求了"不算批准。

### 3. 它找你验收的时候，照着步骤一条条测

它会给你交付物、验收步骤和通过标准。你挨个试：通过就说"验收通过"；出问题就直接描述——"XXX 有 bug，具体表现是 XXX"。它会返工出新的版本，你再验一次。

### 4. 纯聊天打个招呼

如果只是随口问问、讨论个想法，跟它说一句：

> 一个纯问答：XXX

这样它就不会给你建任务账本，也不会让你审批计划。

## 三、几个容易搞混的点

- **"写了计划" ≠ "你批准了"**：计划落盘只是提案，你点头才生效。
- **"它说做完了" ≠ "你验收通过"**：这两件事是分开记的——它可以标"已完成"，但验收状态仍然是"等待你验收"。
- **它不能替你说"验收通过"**，也不能把没做完的步骤标成做完。
- **决定记录只追加、不改写**：你后来改主意了，它会补一条更正，而不是偷偷把旧的改掉——所以"谁在什么时候批的什么"永远查得到。
- **小活升级成正式任务后不会再降回去**：避免为了图省事，把该留痕的活降级成不留痕。

---

**一句话总结**：它把"AI 干了什么、谁批的、做到哪、下一步能不能动"变成硬盘上可查、可交接、可恢复的记录，而不是靠模型在越来越长的对话里自己记。
