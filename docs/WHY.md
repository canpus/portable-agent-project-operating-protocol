# 为什么 Agent 项目需要状态机

[返回 README](../README.md) · [查看状态机怎样工作](HOW.md) · [安装指南](INSTALL.md)

## 一句话说明

Agent 能连续做很多事，但一次对话并不是可靠的项目记录。状态机把“现在做到哪里、已经批准什么、下一步允许做什么”变成可检查的文件和明确的流转规则。

它不是为了让流程看起来更正式，而是为了防止长期任务在对话变长、模型更换、上下文压缩、返工和多次验收之后逐渐失去共同事实。

## 没有状态机时，常见问题是什么

### 1. 对话还在，细节已经不在了

长对话可能被自动压缩。模型通常还能记住一个大概方向，却可能丢失这些细节：

- 用户明确排除的范围；
- 某个方案为什么被拒绝；
- 哪个 Plan 版本才获得批准；
- 某个外部动作是否已经执行；
- 测试到底运行过，还是只计划运行；
- 下一步从哪里继续最安全。

如果这些事实只存在于聊天记录里，恢复时就只能依靠摘要或模型猜测。

PAPOP 把最终 Goal、Plan、用户 Decision、Current State 和历史 Snapshot 分开保存。压缩后先从文件恢复，再核对实际工作区。

### 2. “用户让我做这个项目”被误解成“所有动作都批准了”

一个项目授权不等于每个动作都获得授权。例如“帮我发布网站”不一定包含购买域名、删除旧站点、覆盖生产环境或向第三方发送私有材料。

状态机把授权分成可识别的关卡：

- 严格模式要求精确确认 Requirements、Goal、Plan 和 Delivery；
- 自主模式允许 Agent 在 Task 授权范围内连续推进；
- 两种模式都会在缺少关键决定、需要具体外部授权、遇到用户关卡或准备改变最终 Goal 时暂停。

这样，Agent 不必为每个小步骤反复询问，也不能用一次笼统授权跨过真正重要的决定。

### 3. 计划变了，旧批准却被继续使用

长期项目经常返工。最危险的情况不是返工本身，而是 Plan 已经发生实质变化，Agent 仍然拿旧版本的“批准”继续执行。

PAPOP 给 Requirements、Goal、Plan 和 Delivery 分配稳定引用。批准或拒绝绑定具体版本。新版本需要新的决定，旧批准不会自动继承到新版本。

### 4. Agent 说“完成了”，但没有可靠证据

模型可以写出很有把握的完成说明，但它可能漏跑测试、误读命令输出、没有检查生成文件，或者把“文件已经产生”误认为“结果符合要求”。

PAPOP 分开记录：

- Agent 是否完成施工；
- 脚本、测试或 diff 是否通过；
- 用户是否验收当前 Delivery。

结构、状态转移、哈希、Snapshot 行号和文件复制由脚本验证。模型的复述不能代替机器证据，Agent 完成也不能代替用户验收。

### 5. 状态写了一半，恢复时不知道哪份是真的

如果 Agent 先改 Current State，随后在写 History 时中断，就会留下彼此不一致的文件。下次对话可能读取其中一份并继续，把错误进一步扩大。

PAPOP 的 checkpoint 工具在写入前检查字段、引用和状态转移，取得 Task 锁，再按固定顺序更新 Current、Snapshot 和 History。它会保存事务信息，并在中途崩溃后按同一事务幂等补齐。只有重新读取验证成功才输出 `CHECKPOINT_COMMITTED`。

### 6. 历史有很多，但找不到当时为什么这样做

把所有内容塞进一个不断增长的大文件，并不能形成可用的记忆。Agent 每次读取全部历史会浪费上下文，也容易在大量文字中抓错重点。

PAPOP 让 `history.md` 成为检索入口。每条历史记录保存关键词和摘要，并连接：

- 对应的 Plan 编号；
- 用户 Decision 编号；
- Case 编号；
- Input 编号；
- Snapshot 在单一 `snapshots.md` 中的精确起止行；
- State 和 Snapshot 的哈希。

查询历史时先搜索 History，再沿指针只读取需要的记录。这样能回答“为什么做、批准了哪个版本、当时做了什么、结果是什么”。

### 7. 同一种错误不断重犯

普通历史可以证明错误发生过，却不一定能在下一次相同场景出现时及时提醒 Agent。

PAPOP 的 Case 保存根因、触发场景、避免方法和发生链。同一 Task 中，同一个已确认根因第三次出现时，系统要求 Agent显式提醒用户，建议把它固化成 Case。只有触发场景匹配时才读取详情，避免每次加载全部教训。

Task Case 只影响当前项目。用户认为它具有强通用性时，可以明确批准升格到工作区或全局；原 Case 和来源链仍然保留。

### 8. 用户给了文件，但来源和归属变得混乱

用户可能先把文件放在工作区根目录，也可能在对话中引用工作区外的文件。如果 Agent直接修改原件，后续很难判断哪些是输入、哪些是任务产物，也可能误删用户文件。

PAPOP 把文件接收设计成独立流程，不改变主状态机：

- 当前 Task 内的文件原地使用；
- 工作区内、Task 外的文件复制并验证后，再询问用户是否删除源文件；
- 工作区外的文件只复制到 `UserInput/`，不询问删除源文件。

## 为什么需要“状态机”，不能只写一份进度说明

一份进度说明只能描述“模型认为发生了什么”。状态机还规定：

- 当前只能处于哪些合法状态；
- 什么条件允许进入下一个状态；
- 哪些转换必须有用户 Decision；
- 哪个版本的 Goal、Plan 或 Delivery 被批准；
- 什么时候必须写检查点；
- 写入失败时怎样停止和恢复；
- 哪些事情仍然未知，不能被写成已完成。

状态机把自然语言承诺变成可以验证的约束。它减少的是“每轮对话重新解释项目”的成本，以及错误恢复后继续扩大的风险。

## 为什么同时提供严格审批和自主推进

不同用户对控制感的要求不同。

严格审批适合这些场景：

- 你希望亲自决定需求、最终 Goal 和阶段方案；
- 返工成本高，施工前多看一次 Plan 更划算；
- 项目需要清楚证明“谁在什么时候批准了哪个版本”；
- 你不希望 Agent 在重要节点自行推断你的意图。

自主推进适合这些场景：

- 任务目标和授权边界已经清楚；
- 你希望 Agent 连续完成调查、修改和验证；
- 普通实现选择不需要逐项审批；
- 只在关键决定、额外授权或你设置的关卡介入。

两种模式共用同一套账本、恢复、机器验证、Case 和文件接收机制。差别在于哪些状态转换必须等待人类。

## 状态机不能解决什么

PAPOP 不能保证模型永不出错，也不能替代：

- Harness 的沙箱、权限和审批机制；
- 操作系统权限；
- Git、云盘或其他备份；
- 生产环境的发布与回滚制度；
- 人类对需求、Plan 和最终交付物的判断。

账本内容也可能写错，所以恢复时必须对照用户最新指令、实际文件、diff、测试和外部状态。状态是恢复入口，不是不可质疑的事实。

## 什么时候值得使用

如果任务会跨多个阶段、可能压缩上下文、需要返工、包含重要用户决定、需要交接或以后还要维护，状态机通常值得使用。

如果你只想让 Agent 遵守基本的文件、Git、依赖、验证和授权纪律，而任务很短、不需要持续状态，可以只安装 GlobalRules Only。
