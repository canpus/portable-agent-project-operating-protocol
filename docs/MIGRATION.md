# v4 迁移与治理模式切换

## 原则

v4 两种模式共用新契约，旧状态不自动转换。迁移不改写过去、不给过去补造批准、不删除用户证据；新模式不能扩大真实权限。

从 v0.2.0 迁入计划审批可保留其核心控制理念；从 v3 迁入任务委托可保留其持续执行理念。v4 不恢复新会话自动建任务、双次续接确认、固定六目录或全项目文件归属结算等旧默认要求。

## 从旧版迁移

1. 备份旧入口、规则及任务账本，保留原路径或可靠归档路径。仓库 legacy/v1 是原有旧规则存档，legacy/v3 保留 v3 活跃规则和当时说明；发布任务原始证据继续保留。
2. 选择一个 v4 包并合并 GlobalRules、项目入口及详细规则。移除旧 OPERATING_RULES/TASK_STATE_MACHINE/SCHEMA 或旧 v3 入口的执行指针；不要两套同时生效。
3. 只迁移还需要继续的任务。读取旧当前状态、所需计划及批准、验收、结果证据，核对当前真实文件与远端结果。不批量重写没有继续价值的账本。
4. 新建 v4 Task，保存原目标、已完成成果、未知项、原记录路径和实际剩余工作；ID 与当前记录不能冲突，历史事实不冒充新发生事件。
5. 计划审批：旧批准作为历史依据保留；剩余工作的 v4 精确提案仍需真实需求确认和批准。旧 rev 的批准不能自动批准新的 v4 PLAN_REF。已有可核验需求确认可记录其真实来源及确认内容，不再要求用户重复同一确认。
6. 任务委托：记录当前有效用户任务授权及其来源/范围。旧状态只有模型摘要而无法核实真实授权时保持待确认；不从旧计划推定新对象、成本或外部授权。
7. 把仍有效的用户关卡、已否定路线、具体交付候选、人工验收状态、未知外部动作和查询标识带入新状态。查询未知外部结果，不重执行业务。
8. 按 checkpoint 保存并读回 v4 状态，注明迁移来源。核验后从新恢复入口继续；旧记录原样保留。

不在迁移时修改业务源码、整理原件或删除旧历史。状态迁移与实际业务工作分开核验。

## 活动任务切换模式

仅用户明确指定目标项目/任务和新模式时执行。维护者更换安装包也要核对活动任务，不能只改配置就丢掉等待状态。

1. 停止新实质工作，按原模式保存；记录正在运行或未知的外部动作。
2. 追加 GOVERNANCE_CHANGED，保存旧/新模式、用户依据、适用任务、既有批准/关卡的处理规则。
3. 更新项目配置及该任务状态。项目内其他活动任务若仍旧模式，保留记录并暂停对其执行，直到用户明确处理；不批量替它们放权。
4. 切入 PLAN_APPROVAL：记录剩余真实工作，使用 TRACKED，提交确认和审批关卡。不补造已完成工作的批准。
5. 切入 TASK_DELEGATION：记录剩余委托范围，保留未被明确撤销的用户关卡；高影响动作授权及宿主权限始终保留。
6. 保存并核验一致的新状态，才按新模式继续。配置/状态冲突且无有效切换决定时只读核查，不选择更宽松者。

“继续”“快点”“直接做”不默认表示改变整个项目治理。用户可以明确释放一个具体关卡，无需切换模式；这种释放也要绑定其目标。

## 已结束任务

已完成旧任务不必迁移。v4 DONE/CANCELLED 恢复默认只报告状态；目标内返工可明确重开原任务，独立新目标另建任务。不要为统一格式改写所有旧账本。
