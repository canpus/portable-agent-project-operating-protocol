# OPERATING_RULES.md — Agent 运行纪律（触发纪律层）

**适用范围**：与同目录 `AGENTS.md` 配套使用。  
**定位**：本文件只定义**条件触发**的执行细节：WHEN（什么证据/情况出现）THEN（切换什么做法）。  
**入口**：执行任何触发动作前，先按 `AGENTS.md` §5 触发索引表定位本节，再局部读取对应章节。  
**层级关系**：本文件 < `AGENTS.md`（宪法层）。与本文件冲突时以 AGENTS 为准；仍有冲突则停止并向用户说明。

> 条款一律写成 WHEN-THEN 形式。永久约束、风险时刻条款与流程开关不在此处（它们在 AGENTS.md）。

---

## 1. 使用约定

1. WHEN 本文件被 AGENTS.md §5 触发索引表引用 THEN 按表定位章节，只读相关章节，不整文件硬读。
2. WHEN 同一条款在 AGENTS.md 与本文件重复 THEN 以 AGENTS.md 为准，并报告重复（应单点写入，本文件负责细节）。
3. WHEN 本文件条款与实际环境能力冲突 THEN 使用语义等价实现；无等价路径则明确说明限制与未完成部分。

---

## 2. 会话归属与续接

WHEN 任何新对话开始 THEN 按 AGENTS.md §1 判定会话归属；本节的判定执行细节如下。

### 2.1 归属判定流程

1. WHEN 对话开始 THEN 先读 `<PROJECT_ROOT>/TASK_INDEX.md`；文件不存在则按"新任务"处理。
2. WHEN 用户首句未提及任何已有任务 THEN 默认建立新任务：创建任务目录、初始化三本账、在 TASK_INDEX.md 写入初始区块。
3. WHEN 用户首句提到某个已有任务（编号或主题）THEN 向用户展示该任务的编号、主题、状态与交接要点，并**询问**："是否继续该任务？"
4. WHEN 用户明确表示继续（双次确认：首句提及 + 对询问的明确肯定）THEN 进入续接（§2.2）；否则按用户意图新建任务或重新确认。

### 2.2 续接协议

WHEN 用户双次确认续接任务 N THEN：

1. **不建立新任务**：不创建新任务目录、不初始化新三本账、**不另立 TASK_INDEX 区块**（任务数量不变，变的只是对话数量）。
2. 完整读取任务 N 的 `task_current_state.md`；按需搜索局部读取 `plan.md` 相关记录。
3. 在新对话的工作记录中记录 `PRECEDING_TASK_REF`（续接来源任务编号 + 续接时间）。
4. 从 `SAFE_RESUME_POINT` 继续，禁止重复生成已存在的 Proposal / History Entry / 正式 ID。
5. 本对话的 Agent 成为任务 N 的**最后活跃 Agent**，接管索引区块维护权（原 Agent 退出维护）；按 §3 更新 `LAST_ACTIVE_AT`。

### 2.3 并行防护

WHEN 续接接管前发现疑似并行（该任务区块 `LAST_ACTIVE_AT` 距今很近，或存在其他活跃迹象）THEN：

1. **直接发出警告**（原文）：
   > 同一任务两个对话并行会严重扰乱账本，导致记忆混乱和项目进度状态丢失，会产生严重的后果。
2. 有义务**确认另一个涉及此任务的 Agent 已结束任务并已落盘所有账本文件**。
3. WHEN 不确定 THEN 尝试与另一个涉及此任务的 Agent 直接确认：
   - 有会话间通信机制 → 使用它；
   - 无通信机制 → 检查可观察证据（账本最后写入时间、活跃标记、文件状态）。
4. WHEN 仍无法确认 THEN 将"警告 + 无法核实另一 Agent 是否已结束"如实告知用户，由用户决定是否继续；**该不确定性与警告原文写入当前任务的账本留痕**。

### 2.4 并行禁令

WHEN 同一任务已有活跃 Agent THEN 禁止并行更改该任务任何账本、索引区块或文件；任何时刻一个任务只有一个活跃 Agent 持有写权。

---

## 3. TASK_INDEX 索引维护

WHEN 任务创建 / 轮次结束 / 续接接管 THEN 按本节维护 `<PROJECT_ROOT>/TASK_INDEX.md`（格式见 SCHEMA TIDX-1）。

1. **投影式**：TASK_INDEX.md 可覆盖，是项目内所有任务 current_state 的简略版；任何时刻反映各任务的当前状态，不承担历史职责（历史在 task_history.md）。
2. **区块独立**：每个任务一个区块；更新前读全文件，**只替换自己的区块**，不得改动其他任务的区块。
3. **写入时机**：
   - 任务创建时：写入初始区块（属于创建动作）；
   - 轮次结束时：更新自己的区块（状态、阶段、交接要点）；
   - 续接接管时：更新 `LAST_ACTIVE_AT` 与活跃标记。
4. **维护权**：归属于该任务的**最后活跃 Agent**；续接会话成为新维护者后原 Agent 退出；**同一任务内禁止并行更改**（§2.4）。
5. WHEN 任务目录被删除/归档 THEN 区块标记 STALE 而非删除（保持可追溯）。

---

## 4. 文件保护与清理

### 4.1 修改既有文件

WHEN 拟修改受版本控制管理的文本文件 THEN 先检查当前状态和相关 diff，在用户已有改动基础上做最小修改。

WHEN 目标为二进制文档、未跟踪文件、非版本控制工作区或无法有效文本 diff 的文件 THEN 通过输出副本、备份、文件元数据、结构检查、内容哈希或格式对应的验证方式保护已有内容；不得因为看不到文本 diff 就假定文件可以覆盖。

WHEN 发现与当前任务无关的用户改动 THEN 不得覆盖、删除、还原或格式化；未经明确要求不得运行可能重写大量无关文件的全项目格式化、自动修复或批量迁移。

### 4.2 原件保护

WHEN 处理 `01_inputs/` 中的原始文件 THEN 不得直接覆盖、污染或删除；需要转换或修改时保留原件，派生结果进入其他目录。

### 4.3 临时文件清理

WHEN 考虑清理 `03_temp/` 中的文件 THEN 仅当同时满足以下全部条件才可清理：

1. 明确由当前 Task 生成；
2. 可可靠重建；
3. 不承担证据或交付作用；
4. 删除不影响后续复查。

`03_temp/` 不因 Task 结束自动获得删除授权。

### 4.4 禁止为整洁而移动

WHEN 文件归属不明确 THEN 先低成本检查；仍无法确定则保持原位；不得为了“整洁”强行移动、删除或归档；不得因此阻塞无关工作。

## 5. 散落文件归属与登记

### 5.1 快速判定三规则

WHEN 发现项目目录中的散落文件 THEN 按以下优先级判定归属：

1. **用户澄清 > 一切默认**：用户在对话中明确说明来源/用途的文件，按澄清归属（无论何时出现）。
2. **会话中提及**：对话开始之后出现、且用户在对话过程中提到过的文件 → 本任务文件。
3. **会话前已有**：对话开始之前就已在项目目录里的文件 → 默认**归属不明（待定）**。

WHEN 归属不明 THEN 默认"待定"，进入登记表等待用户澄清；**禁止反向推定**（"非白名单 = 当前 Task 文件"不成立）。

### 5.2 登记

WHEN 完成一次归属判定 THEN 将结果写入 `<PROJECT_ROOT>/FILE_INDEX.md`（格式见 SCHEMA FIDX-1，append-only 流水）：路径、时间、内容概要、归属（taskN / 公共 / 待定）、证据、状态。

### 5.3 轮次关闭归属结算

WHEN 轮次关闭 THEN 在写历史快照**之前**执行归属结算：

1. 列出本回合涉及但未定归属的全部文件 + 快速判定结果（§5.1）；
2. 请用户裁决：归某任务 / 公共 / 保持待定；
3. 裁决结果写入 FILE_INDEX.md；
4. **之后**才冻结 CurrentState、写历史快照、关闭轮次。

WHEN 用户不响应归属结算 THEN 全部记"待定"写入 FILE_INDEX，不阻塞关闭流程。

---

## 6. 委派与协作

WHEN 派发 Subagent / 委派工作 THEN：

1. Subagent 从属于当前 Top-Level Session 对应的唯一 Task；不得创建新的日期目录、新任务、自行改变状态机阶段。
2. 生命周期账本（plan.md / task_current_state.md / task_history.md / TASK_INDEX.md / FILE_INDEX.md / cases/）默认由主 Agent / 主协调者串行治理；Subagent 不得并发写账本。
3. 委派必须携带 Task 状态：`PROJECT_ROOT`、当前 Task 根路径、允许读写的目录/文件范围、当前 `ROUND_ID`、当前 Approved Plan Ref（如存在）、当前状态机阶段、禁止超范围施工的约束。
4. 不得假定 Subagent 已自动继承全部上下文或本文件内容。

---

## 7. 工具与执行原则

WHEN 使用工具执行操作 THEN：

1. 使用宿主当前真实可用的等效能力（文件读取/浏览、内容搜索、精确编辑、命令执行、版本控制检查、网页检索、文档感知、子 Agent 调度等）。
2. WHEN 工具能直接降低关键不确定性 THEN 应实际使用；工具不可用时明确说明限制，不得把未验证结果写成已确认事实。
3. WHEN 命令、代码、测试失败 THEN 必须读取并分析错误信息；禁止在输入、代码、配置和假设均无变化的情况下机械重复同一操作；只有基于新证据、针对新的根因且风险可控时才继续。
4. WHEN 出现以下情况 THEN 停止当前路径并汇报：针对同一根因连续多次尝试仍无新证据或实质进展；缺少外部权限、凭据或资源；继续操作需要扩大原任务范围；可能造成不可逆损失；错误无法在当前环境可靠验证。
5. WHEN 新证据推翻既有结论 THEN 立即更新结论与任务状态；已被证据否定的方案不得在无新证据时重新出现；结论强度必须与证据强度匹配。

---

## 8. 完成门槛

WHEN 宣布一次交付完成 THEN 至少检查以下全部清单：

- 当前 Top-Level Session 是否始终只有一个 Task；
- 当前 Round 是否使用用户批准的精确 Plan Revision；
- 是否存在未批准的范围扩张；
- `task_current_state.md` 是否反映真实现状；
- 应写入 History 的 CurrentState 是否已完整转写；
- `plan.md` / `task_history.md` 是否保持 Append-Only；
- 是否未经用户显式要求创建 Case；
- Subagent 是否误建 Task 或并发修改生命周期账本；
- 既有项目 canonical assets 是否被错误搬迁；
- 当前 Task 新增输入是否得到保护；
- 独立交付物是否位于 `06_outputs/`（若该任务确有独立交付物）；
- 软件/配置修改是否保留在正确 canonical path；
- 必要验证是否真实执行；
- 长账本读取是否遵守 Search First / Read Narrow；
- **触发索引表（AGENTS.md §5）是否被遵守**；
- **TASK_INDEX.md 中本任务区块是否已更新**；
- **FILE_INDEX.md 登记与归属结算是否完成**（§5.2/§5.3）。

状态转换细节以 `TASK_STATE_MACHINE.md` 为准。
