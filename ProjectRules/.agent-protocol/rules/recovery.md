# 共用恢复、授权核验与记录修复

## 正常恢复

1. 优先用户给定 TASK_ID/current_state 路径；否则读 active，不匹配再搜索 task_index。明确目标不双次确认，多候选无法区分才询问。
2. 完整读取 current_state，核对 Schema、TASK_ID、GOVERNANCE_MODE、工作/授权/验收状态、活动和待批计划、决定引用、最后事件/快照。
3. 项目配置与状态模式冲突时查 GOVERNANCE_CHANGED 决定；没有有效明确切换依据则保持只读核查，不自行选择宽松模式。
4. 检查 LAST_SNAPSHOT 存在，在 history 精确定位 LAST_EVENT_ID 对应块，核对计划、决定、候选和事件关联字段。异常先修复。
5. 精确读取活动 PLAN_REF 和待批 PROPOSED_PLAN_REF 的独立计划块；按决定 ID 读取需求确认、计划批准/任务委托、人工接受及当前相关动作/关卡决定。不全读长期账本。
6. **核验授权**：PLAN_APPROVAL 的当前施工批准须绑定当前精确计划、真实确认需求和范围；待批新修订不能复用旧批准。TASK_DELEGATION 须核对委托请求范围及人工关卡。UNKNOWN 来源不能授予批准。
7. **核验实际世界**：读取下一步依赖的实际文件、候选指纹、后台/远端结果和用户最新指令。证据冲突以新检查点修正，旧状态不能扩大权限。
8. 读取下一动作缺失的规则；在原有关卡允许时继续。AWAITING_PLAN_APPROVAL、AWAITING_ACCEPTANCE 和其他未释放关卡必须保持等待，“恢复/继续”不是自动批准。
9. DONE/CANCELLED 默认只报告状态，不自动重执行业务。用户明确请求返工按 lifecycle 重开；未知外部动作先查询，不重复执行。
10. 下一正常检查点将 RESUME_MODE 改回 NORMAL；确有交接价值可保存 RESUMED，不为改字段制造空事件。

## 修复规则

先暂停冲突写入，只修复能由现有文件、真实用户来源和实际结果确认的状态。快照/history 内容完整不代表授权真实。

- **current 有效、snapshot 缺失**：核对计划、决定、业务结果后复制同 ID 快照；如 history 已存在核对其字段；追加后续 RECOVERY_REPAIR。
- **current/snapshot 有效、history 缺事件**：根据两者补原事件，不重新施工；防重复后另存 RECOVERY_REPAIR。
- **前置 plan/decision 已追加，current 未提交**：检查该块完整性和真实用户来源。真实批准可完成状态提交；待批提案不能据此激活。修复不得重新请求已核实的同一个批准，也不得补造缺失批准。
- **current 缺失/损坏**：检查 prev、history 最后结构完整事件所指 snapshot、对应 plan/decision，选择最近可核验状态；再核对其后实际改动与外部结果。不能只依据最后写入时间盲信 next。
- **存在 next**：视为未提交线索，核对 ID、关联快照/历史、计划/决定及实际结果后决定是否完成；不覆盖更新的用户内容。
- **快照与 current 内容冲突、同 ID 不同块**：暂停冲突写入，列出差异；不能回写旧不可变快照。无法判定来源请用户裁决，继续允许的只读调查。
- **批准/验收引用缺失或目标不一致**：不能由工具成功、计划文字或模型推断填补。保持对应等待状态，查实际用户决定；无法核实则指出缺少的具体批准/候选依据。
- **索引过时或丢失**：依据有效 current 追加索引修正事件，不回写旧事件，不让索引覆盖任务状态；该任务实际关闭条件仍由治理模式决定。

## 检索与外部动作

稳定 ID 搜索后读取对应 BEGIN/END 块；无命中检查路径、版本、拼写和转义。快照全文只在异常、审计或需要还原某时点事实时读。

旧授权只覆盖原对象、动作、数据和成本；变化重新核查。INTENT 不能证明成功，必须查 EXTERNAL_RESULT、收据或远端状态。无法确认就 UNKNOWN，不重复发送、购买或部署。
