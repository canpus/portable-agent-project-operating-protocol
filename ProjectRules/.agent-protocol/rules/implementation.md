# 软件实现、调试与依赖

## 触发

创建、修改、调试或评审可执行代码、脚本、应用配置或构建逻辑。

1. 先读取与目标有关的入口、调用处、接口、依赖声明和现有测试方式。源码与运行证据优先于旧说明；不无目的读取整个仓库。
2. 明确当前计划步骤的成果和验收条件。一个修改围绕一个可解释目标，优先小范围、可回退的实现，不为架构美观顺手重构。
3. 调试时读取原始错误和必要调用路径。能低成本复现就复现；不能稳定复现时说明限制，使用日志、输入、状态和针对性检查建立证据，不虚构根因。
4. 接口变化明确输入、输出、错误行为和副作用。不得静默吞掉异常；保留足以定位问题的上下文，同时避免记录凭据和无必要业务数据。
5. 沿用项目已有日志和可观测性体系。长期服务根据故障影响补充必要日志；一次性脚本不强制建立轮转、关联 ID 和完整日志基础设施。
6. 依赖优先使用项目现有包管理、锁文件、虚拟环境或容器。持续依赖同步声明和必要说明；一次性分析工具不加入生产依赖，不擅自安装到系统或用户全局环境。
7. 执行与风险相称的测试和静态检查，覆盖受影响行为及重要失败路径。不能运行的检查说明原因；启动成功、编译成功或单条测试通过不自动证明目标功能正确。
8. 相关检查通过后停止。只有新修改、失败或未解决疑点才扩大验证；不修复无关历史告警来美化结果。
9. 失败后根据新证据改变方法。多次尝试仍有新信息可继续；没有新假设、缺少权限/资源或无法可靠验证时停止该路径，说明具体阻塞并寻找任务内替代方案。
