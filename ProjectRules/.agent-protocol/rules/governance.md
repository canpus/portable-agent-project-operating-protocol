# 共用授权、人工决定与治理切换

## 适用与不变量

任何实际执行、人工决定、用户关卡、验收和模式切换都适用。本文件与当前模式规则共同定义授权；全局真实权限和宿主限制始终有效。

1. 计划、检查点、测试成功、模型判断和工具审批都不能伪装成用户批准精确业务计划或用户接受交付。
2. PLAN_APPROVAL 的实质施工需要当前精确 PLAN_REF 的 PLAN_APPROVED 决定；TASK_DELEGATION 的常规工作需要用户任务请求及其范围依据。
3. 高影响动作还需具体对象、动作、数据、成本和影响的授权。计划批准不能自动授权其中列明需另批的动作。
4. 当前模式和审批关卡不能由模型自行放宽。“继续”不自动批准未批准的新计划，不释放所有关卡，也不证明用户已接受交付。

## 实质施工与审批前允许工作

- 实质施工包括修改业务/项目文件、改变程序行为、生成正式交付候选、外部写操作及其他改变用户资产或外部状态的工作。
- 计划批准前允许：必要只读搜索、读取、诊断；不改变项目或外部状态的低风险验证；写入协议自己的计划、状态和决定记录。
- 低风险验证不得借名执行安装、会修改业务数据的测试、项目配置变更或外部写操作。不能安全只读验证时，提出方法供计划审批。
- 已批准范围内、不改变目标/交付物/核心约束的实现细节可调整；实质范围变化按当前模式规则处理。

## 决定记录

TRACKED 任务使用 decisions.md 的 DECISION 块；实际用户决定与普通执行事件分开。

1. 根据现有 DECISION_ID 选择下一个 D- 编号。追加前搜索同 ID，结果未知先检查，不重复写入。
2. 记录类型、TASK_ID、目标 TARGET_REF、精确 PLAN_REF/DELIVERY_REF/ACTION_ID（无关写 NONE）、用户短原文或可靠语义、可取得的消息引用及确认范围。不保存完整聊天、凭据或无必要隐私。
3. REQUIREMENTS_CONFIRMED 决定必须包含人类实际确认的需求摘要、范围、约束和验收条件。PLAN_APPROVED/REJECTED 必须绑定精确修订，记录批准范围与排除项。DELIVERY_ACCEPTED/REJECTED 必须绑定具体交付候选及其路径/指纹。
4. TASK_AUTHORIZED 可来自明确行动请求；它不冒充 PLAN_APPROVED。没有用户来源时标 UNKNOWN，不伪造决定。
5. 追加并读回决定，再更新 current_state 的有关引用并保存 USER_DECISION 检查点；决定存在不等于引用、状态和授权已经完整提交。
6. 旧决定只追加更正，不回写。执行前核对其真实来源、目标和范围；新计划修订不能借用旧修订的批准。

## 用户指定关卡

用户可以要求“先审计划”“完成调查后等我”“发布前确认”等。使用 current_state 的用户关卡表保存 GATE_ID、目标 PLAN_REF/STEP_ID/ACTION_ID 或明确边界、状态 PENDING/RELEASED、释放决定引用。

- 未释放关卡阻塞其覆盖动作，与是否低风险、是否 FAST 无关；AUTO 任务出现关卡立即 TRACKED。
- 对关卡的明确批准记录 USER_GATE_RELEASED，绑定具体 GATE_ID 和范围；如果关卡唯一目标就是同一精确计划，PLAN_APPROVED 可直接作为该关卡的释放引用，不重复制造第二个决定。一个批准不能释放无关关卡。
- TASK_DELEGATION 中“先审计划”要求绑定精确修订。修订改变该批准覆盖的执行范围时，新提案继续待批；不把旧关卡批准挪给新修订。
- 正式计划记录关卡及必要的另行审批。关卡变更和撤销只有明确用户指令才能生效，记录 USER_GATE_CHANGED；不由模型判断“已不重要”自行撤销。

## 人工验收

- 检查通过只能证明 Agent 侧验证结果，不能写 ACCEPTANCE_STATUS: ACCEPTED。
- 交付候选使用递增 DELIVERY_REF: B-0001，记录实际路径、版本/哈希或稳定变化证据。新候选分配新 REF，旧候选的接受不覆盖新候选。
- 没有可绑定的明确验收反馈时保持 AWAITING 或 NOT_REQUESTED。拒绝时记录反馈、候选和待修复项。
- PLAN_APPROVAL 始终等待人工验收后完成任务；TASK_DELEGATION 用户指定人工验收时也等待，否则可完成 Agent 侧工作，ACCEPTANCE_STATUS: NOT_REQUIRED，仍不能声称人类已接受。

## 模式切换

1. 仅用户/维护者明确要求切换目标项目或任务的治理模式时才处理；不把“快点”“继续”“直接做”默认解释为长期放宽规则。
2. 停止新实质工作，保存原模式检查点，保留批准、未释放关卡、候选和未知外部动作。正在运行的动作先收取或记录查询方法。
3. 记录 GOVERNANCE_CHANGED 决定，包含旧/新模式、用户依据、适用任务、既有批准如何处理。项目配置与有效 current_state 必须一致；未明确如何处理冲突的其他活动任务，保留其模式且不对其执行。
4. 切入 PLAN_APPROVAL：使用 TRACKED。已有真实成果保留为事实；重新确认剩余需求、提交剩余工作的计划并等待批准，不补造过去批准。
5. 切入 TASK_DELEGATION：记录剩余任务的委托范围。已有人工关卡和高影响动作授权要求仍保留，除非用户明确撤销具体可变关卡；真实权限不能撤销。
6. 新状态保存并读回后才在新模式执行。配置/状态冲突且没有真实切换决定时保持只读核查，不能自动选择更宽松者。
